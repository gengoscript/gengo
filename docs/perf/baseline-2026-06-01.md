## After GC threshold tuning (Phase 6a)

| Case | before_ms | after_ms | delta |
|---|---|---|---|
| 010_string_concat_heavy | 806 | 733 | −9% |
| 001_compute_stress | 128 | 128 | 0% |

**010 gc_runs:** 11,880 → 4,520 (−62%). GC time: ~192ms → 73ms.  
**001 gc_runs:** 723 → 723 (unchanged). Driven by managed-slice allocation failure, not object-count threshold.

`gc_object_step` added to all config presets: dev=256, stress=512, tiny=64 (was hardcoded 64 everywhere).
When live objects are few, the new threshold delays GC by 256 allocations instead of 64 — 4× less frequent GC for workloads with low steady-state object counts (string chains).
Compute_stress GC is driven by heap exhaustion in `vmAllocManagedSlice`; each O(2048) sweep costs ~20 µs. Previously, a GC triggered inside `concatDynString` could sweep the source strings and return their backing bytes as the destination, triggering a `@memcpy` alias panic under high allocation pressure.

## Observations

1. **fib_recursive is pure call overhead**: `constant`, `get_local`, `call`, `ret` dominate. The repeated `constant` load before comparisons is the single biggest target for a superinstruction.

2. **get_global is #1 across nearly every workload**: Named global lookup (hash scan) appears in every top-10. This is the highest-value IC target after struct field access.

3. **compute_stress has 723 GC runs**: Struct allocation in a loop. `get_field`/`invoke_method` are high because it accesses struct fields on every iteration.

4. **No map probe data**: The bench workloads don't exercise `map_hashed` lookups at scale. The map probe counter infrastructure is in place but needs a map-heavy bench case.

5. **String concat bytes = 0 across all benches**: Existing bench suite has no string-heavy workloads. A new bench case is needed to exercise the concat path.
